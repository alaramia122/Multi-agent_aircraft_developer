# Реестр внешних инструментов агентов

## Назначение

Connector/Tool Registry является каталогом разрешённых возможностей. Он не исполняет инструменты и не заменяет Gateway authorization.

Агент может выбрать инструмент только по его идентификатору из доступного набора. Сам идентификатор не является разрешением на выполнение.

## Trust levels

Уровни строго упорядочены:

1. UNTRUSTED — инструмент только зарегистрирован.
2. SANDBOX — разрешено изолированное экспериментальное использование.
3. PROJECT_VERIFIED — проверен в рамках проекта.
4. ENGINEERING_VERIFIED — допущен для инженерных операций.
5. OPERATIONALLY_ALLOWED — разрешён для эксплуатационного применения.

Повышение trust level является отдельным governance-действием и не выполняется LLM автоматически.

## Разрешения

Каждый инструмент объявляет операции и требуемый уровень авторизации. Также фиксируется side effect: NONE, READ, WRITE или PHYSICAL.

Наличие WRITE или PHYSICAL не должно автоматически давать агенту соответствующее право. Фактический вызов обязан пройти Gateway authorization.

## Пользовательские инструменты

Пользователь может зарегистрировать собственный инструмент через будущий административный интерфейс. Минимальная запись должна содержать:

- уникальный tool_id;
- название и описание;
- контракт версии;
- trust level;
- операции;
- требуемые authorization levels;
- side effects;
- область проекта;
- схему конфигурации.

Новый инструмент по умолчанию имеет UNTRUSTED.

Пример CAD-инструмента: cad.solidworks.export-model может быть зарегистрирован как UNTRUSTED и использоваться только после предусмотренной процедуры верификации. Нельзя просто добавить описание инструмента и получить доступ к критическим операциям.

## Выбор инструмента агентом

Будущий агент получает каталог доступных инструментов и выбирает из него подходящий по задаче. Оркестратор/Gateway дополнительно проверяет:

1. существует ли tool_id;
2. включён ли инструмент;
3. достаточен ли trust level;
4. разрешена ли конкретная операция;
5. соответствует ли authorization level текущего Actor;
6. допустимы ли side effects для текущего workflow/assurance profile;
7. должен ли потребоваться человек.

## Текущая реализация

Сейчас реализованы только domain-контракты и детерминированный in-memory registry. Исполнительный адаптер, persistent registry, UI регистрации, policy engine и MCP-инструмент вызова будут отдельными следующими слоями.

Это намеренно: каталог возможностей не должен одновременно становиться произвольным execution runtime.
