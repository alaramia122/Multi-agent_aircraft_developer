# Реестр внешних инструментов агентов

## Назначение

Tool Registry — каталог метаданных и разрешённых возможностей. Он не является произвольным runtime и не заменяет авторизацию Gateway. Агент выбирает инструмент только по `tool_id` из доступного каталога; знание идентификатора не даёт права на вызов.

## Модель доверия

Уровни упорядочены от меньшего доверия к большему:

1. `UNTRUSTED` — зарегистрирован, но не допускается к вызову агента.
2. `SANDBOX` — разрешено только изолированное экспериментальное использование.
3. `PROJECT_VERIFIED` — проверен в контексте проекта.
4. `ENGINEERING_VERIFIED` — допущен для инженерных операций.
5. `OPERATIONALLY_ALLOWED` — разрешён для эксплуатационного применения.

Повышение уровня доверия и включение инструмента — отдельные governance-действия. LLM не может выполнять их автоматически.

## Контракт инструмента

Версионированный `ToolDescriptor` содержит идентификатор, название и описание, версию контракта, уровень доверия, список операций и требуемые уровни авторизации, типы побочных эффектов (`NONE`, `READ`, `WRITE`, `PHYSICAL`), признак проектной области, состояние `enabled` и схему конфигурации.

Схема конфигурации — описание ожидаемых параметров, а не исполняемый код. Реестр не хранит произвольные команды, скрипты или секреты.

При создании descriptor Gateway также проверяет семантическую корректность контракта: каждый `authorization_level` должен соответствовать одному из `L0_READ`, `L1_PROPOSE`, `L2_MODIFY_WORKSPACE`, `L3_APPROVE`; повторяющиеся имена операций запрещены, поскольку они создают неоднозначность при выборе разрешения. Это не заменяет проверку прав во время вызова.

## Регистрация пользовательского инструмента

MCP-операция `register_custom_tool` доступна только человеку с уровнем `L2_MODIFY_WORKSPACE`. Gateway не доверяет переданным клиентом полям `trust_level` и `enabled`: при регистрации принудительно устанавливаются `UNTRUSTED` и `enabled=false`. Пользовательский descriptor не может объявлять операции уровня `L3_APPROVE`.

Метаданные сохраняются в PostgreSQL в таблице `tool_registry`; попытка регистрации дублирующего `tool_id` отклоняется. События регистрации и вызова записываются в audit.

## Обнаружение и вызов

MCP предоставляет операции:

- `list_available_tools` — детерминированный список включённых инструментов не ниже указанного порога доверия;
- `invoke_engineering_tool` — вызов по `tool_id` и имени операции через Gateway policy;
- `register_custom_tool` — регистрация пользовательского descriptor в выключенном и недоверенном состоянии.

Перед выполнением Gateway проверяет существование инструмента, `enabled`, уровень доверия, зарегистрированную операцию, текущего request-scoped `Actor`, уровень авторизации, область проекта и побочные эффекты. Инструменты с `PHYSICAL` эффектом блокируются до появления отдельного safety gate. AI не может выполнить операцию `L3_APPROVE`.

Для `gateway.git.snapshot` аргумент `ref` принимается как точное имя Git-ссылки, `HEAD` или полный object ID. Выражения ревизий (`HEAD~1`, `^{tree}` и подобные) отклоняются: результат снимка должен однозначно фиксироваться конкретной ссылкой/объектом, а не произвольным выражением обхода истории.

Выполнение возможно только через явно подключённый `ToolExecutionAdapter`. Если adapter отсутствует, вызов отклоняется с audit-событием; Gateway не запускает код из descriptor.

## Текущие ограничения и следующий шаг

Реализованы PostgreSQL-реестр, MCP-регистрация/обнаружение/вызов, policy-проверки и audit. **Не реализованы** административный процесс проверки и активации инструмента, контролируемое повышение trust level, пользовательский интерфейс управления, а также конкретные production `ToolExecutionAdapter`. Поэтому регистрация пользовательского инструмента пока сохраняет его метаданные, но не делает инструмент исполняемым.

Следующий этап — добавить отдельный контролируемый жизненный цикл проверки/активации и подключать конкретные адаптеры только через явную конфигурацию и тесты. Не следует разрешать агентам произвольно выполнять пользовательские команды.
