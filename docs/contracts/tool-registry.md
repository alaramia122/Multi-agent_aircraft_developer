# Реестр внешних инструментов агентов

## Назначение

Tool Registry — каталог метаданных и разрешённых возможностей. Он не является произвольным runtime и не заменяет авторизацию Gateway. Агент выбирает инструмент только по `tool_id` из доступного каталога; знание идентификатора не даёт права на вызов.

## Модель доверия

Уровни упорядочены от меньшего доверия к большему:

1. `UNTRUSTED` — зарегистрирован, но не допускается к вызову агента.
2. `SANDBOX` — разрешено только изолированное экспериментальное использование.
3. `PROJECT_VERIFIED` — проверен в контексте проекта.
4. `ENGINEERING_VERIFIED` — допущен для инженерных операций.
5. `OPERATIONALLY_ALLOWED` — разрешён для эксплуатационного применения.

Повышение уровня доверия и включение инструмента — отдельные governance-действия. LLM не может выполнять их автоматически.

## Контракт инструмента

Версионированный `ToolDescriptor` содержит идентификатор, название и описание, версию контракта, уровень доверия, список операций и требуемые уровни авторизации, типы побочных эффектов (`NONE`, `READ`, `WRITE`, `PHYSICAL`), признак проектной области, состояние `enabled`, состояние жизненного цикла и схему конфигурации.

Схема конфигурации — описание ожидаемых параметров, а не исполняемый код. Реестр не хранит произвольные команды, скрипты или секреты.

При создании descriptor Gateway также проверяет семантическую корректность контракта: каждый `authorization_level` должен соответствовать одному из `L0_READ`, `L1_PROPOSE`, `L2_MODIFY_WORKSPACE`, `L3_APPROVE`; повторяющиеся имена операций запрещены, поскольку они создают неоднозначность при выборе разрешения. Это не заменяет проверку прав во время вызова.

## Регистрация пользовательского инструмента

MCP-операция `register_custom_tool` доступна только человеку с уровнем `L2_MODIFY_WORKSPACE`. Gateway не доверяет переданным клиентом полям `trust_level` и `enabled`: при регистрации принудительно устанавливаются `UNTRUSTED`, `enabled=false` и `lifecycle_state=PENDING_REVIEW`. Пользовательский descriptor не может объявлять операции уровня `L3_APPROVE`.

Метаданные сохраняются в PostgreSQL в таблице `tool_registry`; попытка регистрации дублирующего `tool_id` отклоняется. События регистрации, проверки, отзыва и вызова записываются в audit.

## Обнаружение и вызов

MCP предоставляет операции:

- `list_available_tools` — детерминированный список включённых инструментов не ниже указанного порога доверия;
- `invoke_engineering_tool` — вызов по `tool_id` и имени операции через Gateway policy;
- `register_custom_tool` — регистрация пользовательского descriptor в выключенном и недоверенном состоянии.

Перед выполнением Gateway проверяет существование инструмента, `lifecycle_state=ACTIVE`, `enabled`, уровень доверия, зарегистрированную операцию, текущего request-scoped `Actor`, уровень авторизации, область проекта и побочные эффекты. Инструменты с `PHYSICAL` эффектом блокируются до появления отдельного safety gate. AI не может выполнить операцию `L3_APPROVE`.

Выполнение возможно только через явно подключённый `ToolExecutionAdapter`. Если adapter отсутствует, вызов отклоняется с audit-событием; Gateway не запускает код из descriptor.

## Проверка, активация и отзыв

Новый пользовательский инструмент попадает в `PENDING_REVIEW`, остаётся выключенным и недоверенным. Отдельный человеческий HTTP-контур `/human/tools/{tool_id}/review` принимает решение только от проверенного человека с `L3_APPROVE`. При одобрении требуется HTTPS-ссылка на evidence; инструмент переводится только в `ACTIVE` с уровнем `SANDBOX`. Более высокий уровень доверия этим действием не выдаётся. Отклонение переводит инструмент в `REJECTED`; человек с L2/L3 может отозвать активный инструмент, что выключает его и возвращает уровень доверия к `UNTRUSTED`. Повторный review не разрешён. Решения фиксируются в audit.

MCP не предоставляет операций одобрения или отклонения. AI не может выполнять review, повышать доверие или активировать инструмент. Отсутствующий `ToolExecutionAdapter` продолжает приводить к отказу при вызове: активация метаданных не создаёт исполняемый код и не устанавливает адаптер.

Реализованы PostgreSQL-реестр, MCP-регистрация/обнаружение/вызов, fail-closed policy, human L3 review, ограниченная активация в SANDBOX, отзыв и audit. Пока не реализованы автоматизированная песочница исполнения, повышение доверия выше SANDBOX, административный интерфейс и пользовательские production adapters.
